= Documentation Review
:toc: left
:toclevels: 2

Scope: all AsciiDoc files (root `README.adoc`, the `doc/` tree, module READMEs), Javadoc across all modules (spot-checked, prioritizing public API), and `CLAUDE.md` claims versus the build. Reviewed at commit `62313b0`. Every reported mismatch was verified against both the documentation and the code.

Structure is strong: `doc/README.adoc` is a complete working index; every cross-file link, image, and include target in all 31 AsciiDoc files resolves (verified programmatically — one intra-file xref broken, DOC-12). Coverage is very good for the gateway reference. The findings below are the exceptions.

== Major findings

=== DOC-01 — Configuration reference claims user routes support prefix matching; they do not

* Severity: MAJOR | Category: doc-code-mismatch | Confidence: confirmed
* Location: `doc/reference/configuration.adoc:452, 500` vs `nifi-cuioss-rest-processors/src/main/java/de/cuioss/nifi/rest/handler/EndpointHandler.java:64`, `GatewayRequestHandler.java:347-350`

The route table says `restapi.<name>.path` "Supports exact paths, prefix matching, and `{placeholder}` templates", and the Path-Parameter section repeats "three ordered passes — exact match, prefix match, then pattern match" as if all apply to user routes. In code, `EndpointHandler.prefixMatch()` defaults to `false` and is overridden to `true` only by the built-in `/status` and `/attachments` handlers; `ApiRouteHandler` never overrides it, so a user route can never prefix-match (a request to a sub-path of an exact route 404s). `nifi-cuioss-rest-processors/README.adoc:5` states the correct behavior ("Prefix matching is not available for user routes") — the project's own docs disagree with each other.

=== DOC-02 — JSON `/metrics` gatewayEvents keys documented as UPPER-CASE; code lowercases them

* Severity: MAJOR | Category: doc-code-mismatch | Confidence: confirmed
* Location: `doc/reference/metrics-api.adoc:159-174`, `doc/architecture/gateway.adoc:393-399` vs `nifi-cuioss-rest-processors/src/main/java/de/cuioss/nifi/rest/handler/MetricsEndpointHandler.java:176-181`

metrics-api.adoc shows `"gatewayEvents": { "MISSING_BEARER_TOKEN": 12, ... }` with an explicit NOTE that the keys "use the *raw* event-type names in upper-case ... unlike the lower-cased Prometheus labels." The code lowercases the enum name (`entry.getKey().name().toLowerCase(Locale.ROOT)`) with a comment saying "one casing across the whole metrics response." gateway.adoc repeats the wrong upper-case keys. Any consumer parsing per the doc's schema NOTE will find no keys.

=== DOC-03 — Doc claims `jwt.error.reason` is set on success FlowFiles for missing-but-not-required tokens; code deliberately does not set it

* Severity: MAJOR | Category: doc-code-mismatch | Confidence: confirmed
* Location: `doc/architecture/jwt-processor.adoc:64, 70` vs `nifi-cuioss-processors/src/main/java/de/cuioss/nifi/processors/auth/MultiIssuerJWTTokenAuthenticator.java:230-237`

jwt-processor.adoc says `jwt.error.reason` is "also set on `success` FlowFiles when token is missing and not required: 'No token provided'" and repeats "(with `jwt.present=false` and `jwt.error.reason` set)". `handleMissingToken` sets only `jwt.present=false`, with an in-code comment: "a missing token is an accepted outcome here, not an error, so jwt.error.reason must not be set on the success FlowFile." Flow designers routing on `jwt.error.reason` presence per the doc would misbehave.

=== DOC-08 — The AUTH-001…AUTH-010 `jwt.error.code` taxonomy is completely undocumented

* Severity: MAJOR | Category: completeness | Confidence: confirmed
* Location: `doc/` (no coverage) vs `MultiIssuerJWTTokenAuthenticator.java:190, 215, 240, 264-278`; acknowledged in `AuthLogMessages.java:30-32`

The processor writes fine-grained error codes to `jwt.error.code` (AUTH-001 missing token, AUTH-002 generic validation failure, AUTH-003 token size, AUTH-005 expired, AUTH-006 signature, AUTH-007 issuer, AUTH-008 audience, AUTH-010 authorization failed). No doc file lists them (`grep AUTH-` in `doc/` returns nothing); jwt-processor.adoc and the guide only say "Error code on validation failure". `AuthLogMessages`' own Javadoc concedes error-reference.adoc "does not cover these codes". Flow designers routing on error codes have no reference. Error *categories* are only partially documented.

== Minor findings

=== DOC-04 — `scopes` claim listed as excluded from `jwt.content.*`; code deliberately preserves it

* Severity: MINOR | Category: doc-code-mismatch | Confidence: confirmed
* Location: `doc/architecture/jwt-processor.adoc:62` vs `nifi-cuioss-common/src/main/java/de/cuioss/nifi/jwt/util/TokenClaimMapper.java:57-59` (and Javadoc 38-42)

The doc says standard claims "(`sub`, `iss`, `exp`, `roles`, `groups`, `scope`, `scopes`) are excluded to avoid duplication". `DEDICATED_CLAIM_KEYS` excludes only `sub, iss, exp, roles, groups, scope`; the class Javadoc explicitly states a non-standard `scopes` claim "is preserved under the `jwt.content.*` prefix rather than being silently dropped."

=== DOC-05 — FlowFile attribute table says only the Authorization header is excluded; code excludes 8 sensitive headers

* Severity: MINOR | Category: doc-code-mismatch | Confidence: confirmed
* Location: `doc/architecture/gateway.adoc:277` vs `GatewayRequestHandler.java:112-114`

A flow relying on `http.header.x-api-key` per the doc would silently miss the attribute.

=== DOC-07 — NiFi version inconsistency: docs/badge say 2.10.0, Maven builds against 2.11.0

* Severity: MINOR | Category: duplication (contradiction) | Confidence: confirmed
* Location: `README.adoc:9` (badge), `doc/reference/configuration.adoc:593` (`apache/nifi:2.10.0`), `integration-testing/README.adoc:61` vs `pom.xml:85` (`<version.nifi>2.11.0</version.nifi>`)

=== DOC-09 — Undocumented `jwksUri` alias for the issuer JWKS URL key

* Severity: MINOR | Category: completeness | Confidence: confirmed
* Location: `doc/reference/configuration.adoc:61-97` vs `IssuerConfigurationParser.java:293-296, 332-334`

`resolveJwksSource`/`hasUrlSource` accept a `jwksUri` property as an alternative to `jwks-url` (e.g. `issuer.<name>.jwksUri`). The issuer dynamic-property table documents only `jwks-url`/`jwks-file`/`jwks-content`. Either document it or mark it internal/legacy.

=== DOC-10 — Reload Behavior section covers only the Controller Service, not the gateway's static-file route loading

* Severity: MINOR | Category: completeness | Confidence: confirmed
* Location: `doc/reference/configuration.adoc:566-568` vs `RestApiGatewayProcessor.java:237-260, 262-274`

The section says files "are loaded once when the Controller Service is enabled (@OnEnabled) ... disable and re-enable the Controller Service" to reload. The `RestApiGatewayProcessor` also loads `restapi.*` from static files (at `@OnScheduled` via a fresh `ConfigurationManager`), so gateway route changes require a processor restart, not a CS toggle. The doc never states how to reload gateway routes from files.

=== DOC-16 — `schema` Javadoc says file path only; inline JSON schemas are supported

* Severity: MINOR | Category: javadoc | Confidence: confirmed
* Location: `nifi-cuioss-rest-processors/src/main/java/de/cuioss/nifi/rest/config/RouteConfigurationParser.java:51`, `RouteConfiguration.java:43` vs `JsonSchemaValidator.java:42, 76`, `doc/reference/configuration.adoc:461`

=== DOC-17 — `@WritesAttributes` annotation is incomplete vs actual attributes written

* Severity: MINOR | Category: javadoc | Confidence: confirmed
* Location: `MultiIssuerJWTTokenAuthenticator.java:81-88`

The annotation lists `jwt.content.*`, `jwt.validatedAt`, `jwt.present`, and the three `jwt.error.*` attributes, but the processor also writes `jwt.subject`, `jwt.issuer`, `jwt.expiration`, `jwt.roles`, `jwt.groups`, `jwt.scopes`, and `jwt.authorized`. NiFi's generated component documentation will under-report the attribute contract.

=== DOC-18 — Gateway processor has no `@WritesAttributes` / `@DynamicProperty` annotations

* Severity: MINOR | Category: javadoc | Confidence: confirmed
* Location: `RestApiGatewayProcessor.java:80-86`

The processor writes ~20 attribute families (`rest.route.*`, `http.*`, `jwt.*`, `rest.trace.*`, `rest.api.pathparam.*`; see `onTrigger` 510-563) and is configured entirely through `restapi.*` dynamic properties, yet carries only `@Tags` and `@CapabilityDescription`. NiFi's built-in documentation view shows neither the attribute contract nor the dynamic-property convention; the adoc docs are the only source.

=== DOC-19 — Interface omits the `IllegalStateException` thrown when the service is not enabled

* Severity: MINOR | Category: javadoc | Confidence: confirmed
* Location: `nifi-cuioss-api/src/main/java/de/cuioss/nifi/jwt/config/JwtIssuerConfigService.java:38-62` vs `StandardJwtIssuerConfigService.java:244-257`

`validateToken` documents only `@throws TokenValidationException`; the implementation also throws `IllegalStateException` when not enabled (and callers depend on it — `MultiIssuerJWTTokenAuthenticator` catches it to yield/rollback). `getAuthenticationConfig` likewise throws undeclared `IllegalStateException`. For a published service-API NAR interface this is a contract gap. Corresponds to code finding CORE-11.

=== DOC-14 — "Reserved names" rule describes only response-level keys, not entry-level reserved keys

* Severity: INFO | Category: ambiguity | Confidence: confirmed

== Overall assessment

*Structure:* strong. `doc/README.adoc` is a complete working index; every cross-file link, image, and include target across 31 AsciiDoc files resolves (one intra-file xref broken, DOC-12). Clear architecture/guides/reference separation; module READMEs are thin pointers into `doc/`.

*Coverage:* very good for the gateway (properties, errors, metrics, tracking, attachments each have dedicated, code-accurate references — unusually precise). Main gaps: the JWT processor's AUTH-xxx error-code taxonomy (DOC-08), log-record identifiers (DOC-11), and NiFi-native component annotations on the gateway processor (DOC-18).

*Biggest risks for a reader:* (1) configuring a user route expecting prefix matching per configuration.adoc and getting 404s (DOC-01); (2) parsing `/metrics` JSON with the documented upper-case gatewayEvents keys (DOC-02); (3) building flow logic on `jwt.error.reason` presence for missing-token success FlowFiles (DOC-03); (4) reverse-engineering undocumented AUTH-xxx codes to route on them (DOC-08).
