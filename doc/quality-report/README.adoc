== Overview

This directory contains the results of a full-repository quality review covering all code and documentation, performed on 2026-08-15 against commit `62313b0` (project version 2.11.0, NiFi 2.11.0).

The review checked for **correctness, consistency, completeness, lack of ambiguity, and duplication**, with special attention to:

* Code correctness including edge cases
* Hidden traps and false feelings of security
* Whether the claimed security posture (in particular *fail-closed* behavior) is fully implemented
* Whether tests are substantive ("real tests") rather than coverage filler, including generator usage and the presence of both positive and negative tests
* Whether documentation (AsciiDoc and Javadoc) is sensibly structured and represents the current code

== Methodology

. Six independent, parallel deep reviews, each scoped to one aspect (three code reviews, two test-quality reviews, one documentation review). Every reported finding cites concrete file/line evidence; assumptions about third-party library behavior (token-sheriff/cui-jwt-validation, Jetty 12, cui-http) are explicitly marked as such.
. An **adversarial verification pass** using clean (fresh-context) sub-agents that re-verified the findings end-to-end against the actual code, with instructions to refute rather than confirm. Each finding carries a `Verification:` verdict; findings that did not survive verification were corrected or removed. See the verification note in each report.

== Severity scale

* *CRITICAL* — exploitable security flaw or data-loss bug requiring immediate action (none found)
* *MAJOR* — real defect, security gap, or misleading contract that should be fixed
* *MINOR* — genuine issue with limited impact; fix opportunistically
* *INFO* — observation, accepted trade-off, hardening/polish opportunity, or positive verification worth recording

== Executive summary

*Security posture.* The core JWT validation path is genuinely fail-closed: no path was found that routes an unvalidated token to success, defaults are secure (HTTPS required for JWKS, private addresses blocked, token size capped), and error paths consistently deny. The two most significant security findings are in the periphery: the UI's `GatewayProxyServlet` endpoint cache can skip the per-user NiFi authorization read (cross-user IDOR on gateway metrics/test endpoints, UI-02), and the gateway's role/scope requirements are silently unenforced whenever a request legitimately carries no token — most notably the default `local-only,bearer` loopback bypass on management endpoints, including the state-mutating `POST /attachments` (GW-02/GW-03).

*Hidden traps.* The most impactful "false feeling of security" items are configuration-surface traps rather than runtime holes: a shipped example configuration advertises security settings (`minKeySize`, `requiredClaims`, `clockSkew`, cache tuning) that no code enforces (CORE-01); the same example's `name:` key silently overrides the `issuer` identifier and breaks issuer matching (CORE-02); the controller service enables "green" with zero valid issuers and only a WARN (CORE-05); and the gateway listens in plaintext on the TLS-conventional port 9443 by default (GW-06).

*Tests.* The test suites are predominantly real, high-quality tests — attack databases against live servers, anti-vacuous guards, enforced coverage thresholds, no skipped tests. The main exceptions: the processors module's "tampered token" tests exercise only a mock (TQJ-01), the real cryptographic validation seam is under-tested at unit level (TQJ-02), and two end-to-end negatives are missing: a genuinely-signed-but-expired token and a Keycloak-outage fail-closed scenario (TQF-01/TQF-02).

*Documentation.* Structurally strong (a complete working index, all cross-file links resolve) and unusually code-accurate for the gateway reference. The main defects are three doc-vs-code contradictions readers will hit (user-route prefix matching claimed but not implemented, DOC-01; `/metrics` JSON key casing documented wrong, DOC-02; `jwt.error.reason` on success FlowFiles documented but deliberately not set, DOC-03) and one large gap: the `AUTH-001…010` error-code taxonomy is completely undocumented (DOC-08).
